# SPACE GASS API Repository Blueprint
**Repository:** `space-gass-api`
**Audience:** Third-party developers and scripters
**Status:** Draft v1.0

---

## 1. Overview

The `space-gass-api` repository is the single source of truth for the SPACE GASS public API ecosystem. It houses the canonical OpenAPI specification, auto-generated SDKs, curated examples, and the public developer documentation site — all kept in lockstep through automated CI/CD pipelines.

> **Design principle:** The versioned OpenAPI spec is the single source of truth for everything generated — clients, API reference, and changelogs. If it can be derived from the spec, it is. If it must be written by hand, it lives in `sdks/**/examples/` or `docs/`.

## 3. Licensing & IP Strategy

We are using a **Dual-License** strategy to be developer-friendly while protecting the SPACE GASS "Blueprint."

| Area | Path | License | Intent |
|---|---|---|---|
| Clients & Examples | `sdks/` | **MIT** | Zero friction for engineering firms (Arup, AECOM, etc.) |
| OpenAPI Spec | `descriptions/` | **CC BY-ND 4.0** | Free to use the spec; forbidden to fork it as a competing service |

A `LICENSE-SPEC` file at the root and a `NOTICE.md` inside `descriptions/` will make the proprietary boundary explicit and unambiguous to any developer who clones the repo.

## 4. Client Generation — Kiota Configuration

Clients in `sdks/csharp/client/` and `sdks/python/client/` are **never hand-edited**. They are fully regenerated by Kiota whenever a new spec is committed.

**`kiota.config.json` (root)**
```json
{
  "version": "1.0",
  "clients": {
    "SpaceGassApi-csharp": {
      "descriptionLocation": "descriptions/preview/openapi-v15.0.0-preview.yaml",
      "outputPath": "sdks/csharp/client/SpaceGassApi",
      "language": "csharp",
      "namespace": "SpaceGassApi",
```

## 5. CI/CD Automation

Three GitHub Actions workflows handle the full pipeline. All workflows run on `ubuntu-latest`.

---

### 5.1 `generate-clients.yml` — Client Generation & Archiving

**Trigger:** Push to `main` where files match `descriptions/current/**`

**What it does:**
1. Detects the version from the incoming filename (e.g. `openapi-v15.1.0.yaml`)
2. Copies the **previous** `current/` spec into `descriptions/archive/vX.X.X/` using the version extracted from its filename
3. Runs Kiota to regenerate `sdks/csharp/client/` and `sdks/python/client/`
4. Opens a Pull Request containing the archived spec and all regenerated client changes for team review before merging to `main`

**Secrets required:** `GITHUB_TOKEN` (built-in, used to open the PR)

> ⚠️ The PR gate is intentional — it gives the team a chance to review breaking changes in the generated client before they land on `main` and trigger a publish.

---

### 5.2 `publish-packages.yml` — NuGet & PyPI Release

**Trigger:** A GitHub Release is published (tag format: `v*.*.*`)

**What it does:** Runs two jobs **in parallel** — one per platform — followed by a validation job:

| Job | Steps |
|---|---|
| `publish-nuget` | Restore → Build → Pack `sdks/csharp/client/` → Push to NuGet |
| `publish-pypi` | Build wheel from `sdks/python/client/` → Push to PyPI |
| `test-examples` | Runs after both publish jobs succeed (see below) |

Both publish jobs must succeed before `test-examples` runs. If either publish job fails, the other is not cancelled — they are independent.

**`test-examples` job steps:**
1. Wait briefly for NuGet and PyPI indexes to propagate the new version
2. Update the package version reference in `sdks/csharp/examples/` and `sdks/python/examples/` to the newly released version
3. Restore and run each example against the published packages
4. Auto-commit the version bumps back to `main`
5. If any example fails — open a GitHub Issue automatically, tagged `bug` and `examples`, with the workflow run URL and failure output included

**Secrets required:** `NUGET_API_KEY`, `PYPI_API_TOKEN`

---

### 5.3 `deploy-docs.yml` — Documentation Site

**Trigger:** Push to `main` (any file)

**What it does:**
1. Installs Node and Zudoku dependencies
2. Runs `zudoku build` — renders the API reference from `descriptions/current/` and compiles MDX pages from `docs/pages/`
3. Deploys the static output to the `gh-pages` branch

**Notes:**
- Uses `actions/checkout` with `fetch-depth: 0` to ensure accurate "Last Modified" dates on doc pages
- The `basePath: "/space-gass-api"` in `zudoku.config.ts` must match the GitHub Pages URL subpath

**Secrets required:** `GITHUB_TOKEN` (built-in, used to push to `gh-pages`)

## 6. Documentation Site

The docs site is hosted on **GitHub Pages** from the `gh-pages` branch, built with **[Zudoku](https://zudoku.dev)** — an open-source, OpenAPI-powered documentation framework by Zuplo.

**URL:** `https://spacegass.github.io/space-gass-api/`

| Section | Source | Generated? |
|---|---|---|
| Getting Started (C# / Python) | `docs/pages/getting-started/` | ✍️ Hand-written MDX |
| API Reference | `descriptions/current/openapi.yaml` | ✅ Auto-rendered by Zudoku |
| Interactive Playground | `descriptions/current/openapi.yaml` | ✅ Built into Zudoku |
| Changelog | Git tags + release notes | ✅ Auto-generated |

Zudoku reads the OpenAPI spec directly and renders a fully interactive API reference — including a built-in request playground — with no additional tooling. The `zudoku.config.ts` wires the spec path, navigation, and GitHub Pages `basePath` together.

**`docs/zudoku.config.ts` (example)**
```typescript
import type { ZudokuConfig } from "zudoku";

const config: ZudokuConfig = {
  basePath: "/space-gass-api",
  topNavigation: [
    { id: "docs", label: "Documentation" },
    { id: "api", label: "API Reference" },
  ],
  sidebar: {
    docs: [
      { type: "doc", file: "pages/introduction.md" },
      {
        type: "category",
        label: "Getting Started",
        items: [
          { type: "doc", file: "pages/getting-started/dotnet.md" },
          { type: "doc", file: "pages/getting-started/python.md" },
        ],
      },
    ],
  },
  apis: {
    type: "file",
    input: "../descriptions/current/openapi.yaml",
    navigationId: "api",
  },
  docs: {
    files: "/pages/**/*.{md,mdx}",
  },
};

export default config;
```

## 7. Versioning Strategy

SDK and package versions **mirror the SPACE GASS Desktop version** to eliminate any ambiguity for end users.

| SpaceGass Desktop | NuGet Package | PyPI Package | Spec Path |
|---|---|---|---|
| v15.0.2 | `SpaceGassApi 15.0.2` | `space-gass-api==15.0.2` | `descriptions/archive/v15.0.2/openapi.yaml` |
| v15.1.0 | `SpaceGassApi 15.1.0` | `space-gass-api==15.1.0` | `descriptions/archive/v15.1.0/openapi.yaml` |

The `descriptions/current/openapi.yaml` always reflects the latest released version. Archiving a previous version is part of the release checklist.

## 8. Preview to Release Workflow

The repo starts in a **preview state** — there is no `current/` folder until the first formal release is made. When the team decides to release:

1. **Internal monorepo:** The release workflow is manually triggered, the version is stamped into the spec using `yq`, and the versioned spec is pushed to the public repo
2. **Rename preview → current:** The `preview/` folder contents move to `descriptions/current/openapi-v{version}.yaml` — this is the first time `current/` exists in the repo
3. **Archive:** The spec is also copied into `descriptions/archive/v{version}/openapi-v{version}.yaml` for historical reference
4. **Update configs:** Three files must be updated to point from `preview/` to `current/`:
   - `kiota.config.json` — `descriptionLocation` for both clients
   - `docs/zudoku.config.ts` — `input` path for the API reference
   - `.github/workflows/generate-clients.yml` — the trigger path
5. **Tag the release:** A GitHub Release is published with tag `v{version}`, triggering `publish-packages.yml` to push to NuGet and PyPI

From this point forward, all future releases follow the same pattern — the previous `current/` spec is archived and replaced by the new version.

> ⚠️ The `preview/` folder remains after first release and is used for the next upcoming version. If there is no active preview, the folder should be left empty with a `NOTICE.md` explaining its purpose.

| Context | Convention | Example |
|---|---|---|
| C# namespace | PascalCase, no acronym caps | `SpaceGassApi` |
| Python module | snake_case | `space_gass_api` |
| NuGet package ID | `SpaceGassApi` | `dotnet add package SpaceGassApi` |
| PyPI package name | `space-gass-api` | `pip install space-gass-api` |
